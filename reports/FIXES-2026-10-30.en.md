# Nine defects in the tool that produced these audits

Written 2026-10-30. This repository's claim is that its numbers can be checked rather than believed. That has to
cover its own mistakes, so each defect below is stated with the figure it changed, the before-state is archived,
and the fix ships as `zk-vocabulary.py` where it is reusable.

## 1. The vocabulary had no word for Zcash

Auditing `zcash/orchard` — the protocol whose Balance property rests entirely on discrete logarithms in the Pallas
group — produced **1 inventory row (AES-256) and 0
Shor-breakable rows** from 49 parsed files.

Not a crash, not a parse error, not a scope or submodule problem — the four causes I check first. The algorithm
registry had no entry for Sinsemilla, RedDSA, Halo 2 or Poseidon, so the scanner opened every file and recognised
nothing in it. A missing vocabulary is invisible from the outside, because its output is indistinguishable from
good news.

Four entries added, each with detection patterns written against a real clone and a positive and a negative test
case. The same commit now measures **69 rows and 41 Shor-breakable**. Across the stack:
**189 rows / 91 Shor-breakable → 678 / 254**, at identical commits.

## 2. A library that implements a primitive does not call it

`ZcashFoundation/reddsa` names RedDSA, RedPallas and RedJubjub **27 times in doc comments and zero times in
code**: the code says `SpendAuth`, `Binding` and `SigType`. The call-shaped pattern found every consumer — `zebra`
imports `reddsa::` and gets 11 rows — and missed the implementation, so the crate that *is* RedDSA reported no
RedDSA.

Fixed with declaration-shaped patterns (`pub trait|enum SpendAuth`, `impl SigType for`, `pub type Randomizer`).
`reddsa` now reports 3 RedDSA rows. Across every Zcash clone checked, those
patterns fire there and in `orchard/src/primitives/redpallas.rs`, which is the RedPallas wrapper, and nowhere
else. This is the second instance of a class already recorded here: `rustls` names HKDF 75 times in
`key_schedule.rs` and no call-shaped pattern reached it either.

## 3. A precision fix that opened a hole, found by publishing it

`halo2_poseidon` was removed from the Halo 2 alternation, on the argument that importing the hash alone is
evidence of Poseidon and not of the proof system — and Poseidon has its own entry.

It does not. `\b[Pp]oseidon` does **not** match `halo2_poseidon`, because the character before "poseidon" there is
an underscore, which is itself a word character, so the boundary is not present. For one commit `use
halo2_poseidon::` was matched by neither pattern. Found by writing that exact import into the self-test of the
tool published here, which is the entire argument for publishing fixes with tests attached rather than describing
them in prose. `(?:\b|_)[Pp]oseidon\w*` accepts a boundary or an underscore and still rejects `position`,
`composition` and `deposition`. No published bundle changes: the one source file in this portfolio that imports
`halo2_poseidon` also names Poseidon 46 times. A latent defect, fixed, with the measured effect stated as nil.

## 4. Three different kinds of evidence were added up as one number

"Inventory rows" mixed a line of source code with a file's name and a dependency's name, and the Shor total
promoted the weakest of them to the standing of the strongest.

| what the row rests on | rows | Shor-breakable |
|---|---:|---:|
| a line of source code | 1 992 | 1 248 |
| the name of a dependency in a manifest | 915 | 0 |
| the name of a source file (low confidence) | 384 | 180 |
| an OpenPGP key committed to the repository | 117 | 117 |
| other (chain mapping, certificates, contracts) | 346 | 168 |

**180 of the Shor-breakable rows rest on a file name**, not on a line of code. That signal
exists for a good reason — `trezor-firmware/crypto/pbkdf2.c` *defines* PBKDF2 instead of calling it, so no
call-site pattern reaches it — and the reports mark it `confidence: low`. A headline figure was quietly promoting
it. The README now publishes the breakdown above before any other number.

## 5. Maintainers' release keys were counted as implemented cryptography

117 rows across the portfolio are OpenPGP primary keys and subkeys committed to repositories — release-signing
keys, in `monero` (62), `bitbox02-firmware` (44), `jade` (4), `libwally-core` (2), both Zcash wallet SDKs (2 each)
and `zebra` (1). Every one of them counted toward "Shor-breakable".

They are real cryptography and they do have to migrate, because a quantum computer forges a release signature as
readily as a transaction one. They are not cryptography those projects implement, and a reader seeing only a Shor
total would take them for it. Each carries `usage: OpenPGP primary key` or `OpenPGP subkey`, so one filter removes
them; the figure is now stated separately rather than left inside.

## 6. "29 post-quantum" meant two different things

One place counted `pqc`; another counted `pqc + hybrid`. The same portfolio was therefore described with two
numbers as though they were one. They are now always stated apart: post-quantum and hybrid.

## 7. The byte budget dropped the project's own code, silently

When a tree exceeded the runner's total-size limit, the order of dropping was alphabetical, so a vendored
dependency sorting before `src/` could take the whole budget — and the report said how many files did not fit but
never which. A hardware wallet's inventory could therefore be an inventory of a vendored GUI.

Both halves are fixed: the budget is spent on the project's own tree before the directories a `.gitmodules` pins,
the report names the files that did not fit and the ones no analyzer reads, it attributes what it did read to the
submodules it came from, and when the project's own source is dropped the description says so as an explicit
warning. With that, `bitbox02-firmware` is re-read here to **2 645 files instead of 721** at the same
commit, and the 518 that still did not fit are named and are every one of them `optiga-trust-m`'s vendored
mbedtls headers.

`krux` is still published at its earlier 98-row bundle. Re-read at full depth it yields 248 rows — but 230 come
from `firmware/MaixPy` and 11 from `src/krux`, with 1,677 files still not fitting. That is a 23% sample whose
composition depends on the order files are visited, and publishing it as an inventory of a hardware wallet would
be worse than publishing the narrower bundle that answers the question a reader has.

## 8. A benchmark counted as deployed exposure

Across nine codebases, **61 inventory rows came from `bench*` files** — a timing harness reported as shipped
cryptography. Fixed earlier and recorded here for completeness: `bitcoin-core/secp256k1` is 32 of 32, not 38 of
38. The ratio and the argument are untouched; the count is smaller and truer.

## 9. A watcher that cried decision at a stranger's paperwork

Not part of this repository, but the same class of error. The script watching a grant application treated any
change in the review queue's depth as a committee decision. On 2026-10-29 it announced one when the queue went
53 → 54 with approvals and declines both unchanged: somebody else had simply filed an application that morning.
Queue depth is now carried as context and never compared; only the decided counts, the application's own state
and a comment from a human wake anything.

## What is not fixed, and one figure withheld

**A library named after its primitive is still missed unless it declares recognisable types.** The general fix is
the one already accepted for file names — a project's own `[package] name` in a manifest is the project telling
you what is in it — and `_cargo_toml` currently reads only the dependency tables and discards it. That is a new
portfolio-wide inventory source, so it lands with a re-audit sweep, not beside a publish.

**Curves are attributed through the constructions over them** — RedDSA → RedPallas/RedJubjub, Halo 2 over Pasta,
Sinsemilla over Pallas — which stops `pallas::Base` generating a row in every file of `orchard`. The cost showed up
immediately: `zcash/pasta_curves`, a repository that implements nothing but that curve arithmetic, audited to 4
rows and **0 Shor-breakable** — a statement that Pallas and Vesta hold no quantum-vulnerable cryptography, the
exact opposite of the truth. That bundle was withheld rather than published, because a figure that wrong is worse
than silence.

**Fixed 2026-10-30 and now published.** The registry has a Pasta entry detected by the curve's *implementation*
rather than its use: `pub mod pallas`, `new_curve_impl!`, `IsoEp`/`IsoEq`. A pattern on `pallas::` or `EqAffine`
would have added a row to almost every file of `orchard` and `halo2`, duplicating what the Sinsemilla, Halo 2 and
RedDSA rows already say through their `parameter` field. The same commit now measures **9 rows and 5
Shor-breakable**, with Pallas and Vesta named as parameters at `src/lib.rs:45` and `:46`. No other bundle changes:
those patterns match nothing in any other clone checked, and no other repository here implements this curve.

**`.cairo`, `.move` and `.vy` have no analyzer.** A coverage limit, deliberate, and stated wherever those figures
appear.

## Check your own tool

`zk-vocabulary.py` carries the vocabulary from §1–§3 and nothing else of this project. No dependencies, no
network, no `git`.

```
python3 zk-vocabulary.py --repo /path/to/checkout     # what is actually in this tree
python3 zk-vocabulary.py --against results.sarif      # ...and what your scanner failed to report
python3 zk-vocabulary.py --self-test                  # check the patterns before trusting their silence
```

Exit status 1 when the tree contains a primitive your tool did not report. `test-zk-vocabulary.sh` runs 14 cases,
four of them against freshly cloned real repositories, including the one that matters: fed the literal output my
own scanner produced for `zcash/orchard` that morning — `["AES-256"]` — it names all five primitives that were
missed.

Portfolio after all of the above: **61 bundles over 53 codebases, 3 754 inventory rows,
1 713 Shor-breakable.** All 61 verify offline from a clean clone.
